# Task: Preview reset and hand check on the epic's preview

## Description

Prove the whole epic on a real deployment before it merges: switch Preview
to Connect, reset the Preview database, and run the full hand check on the
epic branch's preview, on its branch address and its per-deployment
address. That is the same deployment the epic PR shows; the code is
complete once tasks 001–004 have merged into `epic/vercel-connect-auth`.

The stakeholder does the setup, the reset and the sign-ins; the dev chat
guides them through the preview steps in `docs/DEPLOY.md` (written in task
004), reads what it can through the Vercel tools, and records the results.
No agent runs the reset. The epic merges only when this passes. See the
epic's "Implementation Strategy" step 4, "Task 5's hand check" and "Risks".

## Acceptance Criteria

Setup (stakeholder):
- [ ] A Neon snapshot of the Preview database is taken before the reset.
- [ ] Preview's `VERCEL_CONNECT_GOOGLE` is the spike's
      `google/meals-google-spike` connector, linked to Preview and
      Development; Preview's `OWNER_EMAIL` is checked; Preview's
      `BETTER_AUTH_URL` is deleted (otherwise `/family` shows the
      never-created fixed preview's address after an invitation); and the
      preview under test was built after all three changes.
- [ ] The reset runs against the Preview database with the matching
      `--confirm-host`, and its printed counts are recorded.

The app's rules, on the branch address and on the per-deployment address:
- [ ] The owner signs in and is Owner on `/family`.
- [ ] An invited account signs in and becomes a Member.
- [ ] An uninvited account is refused.
- [ ] A removed member is signed out on their next request.

Connect's behaviour:
- [ ] **`email_verified` arrives as true** (the invited sign-up above
      succeeds). If it arrives false, sign-up fails with
      `EMAIL_NOT_VERIFIED`: stop, record it, and ask the stakeholder before
      anything else; the epic does not merge.
- [ ] **`sub` is stable:** the same Google account signing out and in again
      reaches the same account row, not `account_not_linked`.
- [ ] **`sub` source:** whether `sub` is Google's own (numeric) or a
      Connect-specific value, read from the `account` row without
      recording the value itself.
- [ ] **The gateway checks `redirect_uri`:** an authorization request to
      `connect.vercel.com` with the Preview connector and a `redirect_uri`
      on a foreign host is refused.
- [ ] **`prompt=consent` and stored refresh tokens:** try removing both in
      the connector's configuration; record whether Connect allows it and
      what sign-in does afterwards. Put the connector back if sign-in
      breaks.
- [ ] **Billing:** the connector's token-request count for these sign-ins,
      from its Observability tab.

Recorded:
- [ ] `docs/DEPLOY.md` "Result": date, who ran it, each step's outcome,
      `email_verified` value seen, the `prompt=consent` outcome and the
      token-request count. No real emails, ids or `sub` values.
- [ ] The PRD's "What we know" (or the Decision's "Treated as proven"
      list) records the `sub` source and stability, the `email_verified`
      value and the gateway's `redirect_uri` check, as seen.
- [ ] If `sub` is Google's own, `docs/DEPLOY.md`'s connector-replacement
      warning and rollback steps say so; if not, they keep the "another
      reset" wording.
