# Task: Family rules: invitations, roles and invite-only sign-up

## Description

Add the family model and enforce that only the owner email or an invited email can ever become an account. The rules live in plain functions so they can be checked without a browser.

Before writing code, read the relevant guide in `node_modules/next/dist/docs/` as `AGENTS.md` requires, and read Better Auth's installed docs and types rather than relying on memory.

## Acceptance Criteria
- [ ] `user` has a `role` column with values `owner` or `member`.
- [ ] A single-row `family` table holds the family name; an `invitations` table holds name, email (stored lower-case), invited-by, created time and state (`pending`, `accepted`, `cancelled`), with at most one pending invitation per email.
- [ ] One generated Drizzle migration is committed.
- [ ] `src/lib/family.ts` exports `canSignUp(email)`, `inviteMember`, `cancelInvitation`, `removeMember`, `renameFamily` and `listFamily`.
- [ ] `canSignUp` is true only for `OWNER_EMAIL` or an email with a pending invitation, compared case-insensitively.
- [ ] Better Auth's before-user-creation hook refuses creation when `canSignUp` is false or the provider did not verify the email; no user row is written.
- [ ] `canSignUp(OWNER_EMAIL)` is true only while no owner exists. Once there is an owner, that address is treated like any other, so changing `OWNER_EMAIL` later can never create a second owner.
- [ ] After creation: the owner email gets role `owner` and the family row is created with the name "Our family"; an invited email gets role `member` and its invitation becomes `accepted`.
- [ ] A new member's display name comes from their Google profile. The name typed on the invitation is only used to label the pending invitation.
- [ ] `role` cannot be set or changed through any Better Auth client endpoint (declare it as a server-only field); only the creation hook writes it.
- [ ] `inviteMember`, `cancelInvitation`, `removeMember` and `renameFamily` take the acting member and refuse anyone who is not the owner.
- [ ] `inviteMember` refuses an email that is already a member or already pending, with a clear error.
- [ ] `removeMember` deletes the member's sessions, linked accounts and user row, and refuses to remove the owner. Tables that reference `user` use `ON DELETE CASCADE`, so passkeys added by a later task are removed with no change here.
- [ ] With the invite-only hook in place, remove the "do not set the Google variables on any deployment" warning from `.env.example` and `src/lib/auth.ts`.
- [ ] Carried over from the #9 review: `scripts/check-auth.ts` proves `getAuth()` stays request-time, e.g. with `NEXT_RUNTIME` set and `next/server`'s `connection()` stubbed to count calls, asserting one call per `getAuth()`; and the parent's dead `childEnv.PGLITE_DATA_DIR` line is removed (the child makes its own), with temp directories cleaned up on exit.

## Technical Details
- `OWNER_EMAIL` is read from the environment. If it is unset in production, the owner route is closed: before an owner exists nobody can sign up, and once an owner exists, pending invitations still work (Will's decision, 2026-11-10, so `OWNER_EMAIL` can be removed after the owner signs in).
- Keep these functions free of Next.js request APIs so `scripts/check-accounts.ts` can call them against a temporary database.
- Files: `src/db/schema.ts`, `drizzle/*`, `src/lib/family.ts`, `src/lib/auth.ts` (hooks), `.env.example` (warning only), `scripts/check-auth.ts` (carried-over checks).
