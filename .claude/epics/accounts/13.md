# Task: Passkeys: add, remove and sign in

> **Moved out of this epic** (stakeholder's decision, 2026-11-11): passkeys are now their own PRD, `.claude/prds/passkeys.md`, to keep `accounts` to the smallest useful release. Closed as not planned here. Draft PR wgiddens/meals#25 (`claude/issue-13-passkeys`) is parked, reviewed and nearly done, as the starting point for that PRD.

## Description

Let a signed-in member add a passkey (Face ID, fingerprint) and use it to sign in afterwards.

Before writing code, read the relevant guide in `node_modules/next/dist/docs/` as `AGENTS.md` requires, and read Better Auth's installed docs and types rather than relying on memory.

## Acceptance Criteria
- [ ] The `@better-auth/passkey` plugin is enabled in `getAuth()`, and its `passkey` table is in `src/db/schema.ts` with a committed migration.
- [ ] `/account` lists the member's passkeys with a name and created date, and can add and remove them.
- [ ] `/sign-in` offers "Use a passkey"; a registered passkey signs the member in without Google.
- [ ] A passkey can only be added by a signed-in member; it never creates an account.
- [ ] Removing a member with `removeMember` deletes their passkeys, and a deleted member's passkey no longer signs in.
- [ ] `scripts/check-accounts.ts` gains an assertion that removing a member deletes their passkeys.
- [ ] The passkey relying-party id and origin come from `BETTER_AUTH_URL`; in local development they resolve to `localhost`.
- [ ] Browsers without passkey support do not show the passkey controls.
- [ ] Typecheck, lint, smoke and build pass.

## Technical Details
- Confirm the plugin's server and client setup from the installed package's docs.
- Passkeys are bound to the site's domain: note in code comments that changing the production domain invalidates them and members fall back to Google.
- Files: `src/lib/auth.ts`, `src/lib/auth-client.ts`, `src/db/schema.ts`, `drizzle/*`, `src/app/account/page.tsx`, `src/app/sign-in/page.tsx`, `src/components/Passkey*.tsx`, `scripts/check-accounts.ts`.
- Relying party on previews (stakeholder's decision, 2026-11-11): on `VERCEL_ENV=preview`, rpID is the host of `VERCEL_BRANCH_URL` and origin is exactly `https://<VERCEL_BRANCH_URL>`, so each branch preview has its own passkeys; passkey controls show only where the page's hostname equals the rpID. Production and local follow `BETTER_AUTH_URL` / `localhost` as above; production fails closed without `BETTER_AUTH_URL`.
